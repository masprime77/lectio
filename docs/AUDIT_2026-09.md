# Repository audit — September 2026

Read-only audit of the Lectio repo at `dev` (`537b745`). Nothing outside this
file and `docs/RELEASE_NOTES.md` was changed; every candidate below is a
proposal, not an applied edit. No build, test, install or app-launch command
was run — findings come from reading the source, `git log`, and the committed
type declarations.

> **Scope note.** The audit brief describes a single-package repo with `lib/`,
> `main.js`, `preload.js`, `app.js`, `tests/`, `assets/` and `build/` at the
> root. That layout no longer exists: the repo is an npm-workspaces monorepo
> with `packages/core`, `packages/desktop` and `packages/mobile`. Every section
> below audits the paths that actually exist; §5 reports the layout question
> head-on, and §6 answers the `@lectio/core` question given that the split has
> already happened.

## 1. Architecture conformance

### 1.1 Bridge ↔ handler parity

Every `contextBridge.exposeInMainWorld` surface in
[preload.js](packages/desktop/preload.js) resolves to a registered handler, and
every registered handler is reachable from a bridge. Cross-referencing the 41
`ipcRenderer.invoke/send/on` channel names in the two preload files against the
31 `ipcMain.handle/on` registrations in
[main.js](packages/desktop/main.js) and
[ipc-handlers.js](packages/core/src/ipc-handlers.js), plus the 13
`sendToRenderer`/`webContents.send` sites: **no orphans in either direction.**

The eleven bridges are `planner`, `updater`, `saver`, `appInfo`,
`externalLinks`, `settings`, `legalDocs`, `moodleAuth`, `providerAuth`,
`pomodoroTray`, `pomodoroPopup` (main window), plus `pomodoroPopup` on the
popup's own preload
([preload-pomodoro-popup.js:8](packages/desktop/preload-pomodoro-popup.js:8)) —
a deliberate name reuse across two isolated contexts, documented in place.

**One deviation:** the `externalLinks` bridge
([preload.js:53](packages/desktop/preload.js:53)) and its handler
([main.js:571](packages/desktop/main.js:571)) are wired to each other but have
**no renderer caller anywhere**. A repo-wide grep for `externalLinks`,
`openExternal` and `open-external` returns only the definitions themselves. The
comment at [main.js:569](packages/desktop/main.js:569) still says it serves
"the pre-filled feedback/bug-report issue links", but feedback now POSTs
directly to the Vercel endpoint
([app.js:6340](packages/desktop/app.js:6340)), so the GitHub-redirect path it
existed for is gone. See §2.1.

### 1.2 Renderer isolation

[app.js](packages/desktop/app.js) is clean: no `ipcRenderer`, no `require(`, no
`fs.`, no `process.`, no `__dirname`. It reaches the main process only through
`window.planner` (25 call sites), `window.settings` (12), `window.pomodoroPopup`
(10), `window.moodleAuth` (9), `window.saver` (8), `window.updater` (8),
`window.pomodoroTray` (7), `window.appInfo` (5), `window.providerAuth` (3) and
`window.legalDocs` (2). Core is consumed via the browser globals
`window.PlannerCore` / `window.PomodoroCore`
([app.js:409](packages/desktop/app.js:409),
[app.js:451](packages/desktop/app.js:451)) and
`window.LectioMoodle` / `window.LectioMoodleClient`
([app.js:4894](packages/desktop/app.js:4894)), exactly as the vendoring design
intends.

The one `require(` in renderer-loaded code is
[supabase-storage.js:22-24](packages/desktop/supabase-storage.js:22) — inside
the `typeof module !== 'undefined'` branch of a dual-mode wrapper, so it is
dead in the browser and live only when Vitest loads the file in Node
([desktop-supabase-storage.test.js:13](packages/core/tests/contract/desktop-supabase-storage.test.js:13)).
Conformant, not a leak.

### 1.3 Dual-mode discipline in core

Nine of thirteen `packages/core/src` modules carry the dual-mode wrapper, each
attaching exactly one global:

| File | Global |
| --- | --- |
| [planner-core.js](packages/core/src/planner-core.js) | `PlannerCore` |
| [pomodoro-core.js](packages/core/src/pomodoro-core.js) | `PomodoroCore` |
| [storage/migrate.js](packages/core/src/storage/migrate.js) | `PlannerMigrate` |
| [storage/conflict.js](packages/core/src/storage/conflict.js) | `PlannerConflict` |
| [integrations/moodle.js](packages/core/src/integrations/moodle.js) | `LectioMoodle` |
| [integrations/moodle-client.js](packages/core/src/integrations/moodle-client.js) | `LectioMoodleClient` |
| [integrations/moodle-sso.js](packages/core/src/integrations/moodle-sso.js) | `LectioMoodleSso` |
| [integrations/oauth-redirect.js](packages/core/src/integrations/oauth-redirect.js) | `LectioOAuthRedirect` |
| [integrations/lectio-file.js](packages/core/src/integrations/lectio-file.js) | `LectioFile` |

The other four — [semester-store.js](packages/core/src/semester-store.js),
[ipc-handlers.js](packages/core/src/ipc-handlers.js),
[storage/contract.js](packages/core/src/storage/contract.js),

([lectio-core.d.ts:9](packages/mobile/types/lectio-core.d.ts:9)).

**No DOM or Electron creep.** A grep for `document.`, `require('electron')`,
`localStorage` and `navigator.` across `packages/core/src` returns nothing.

**Minor deviation:** [sync-core.js:28-34](packages/desktop/scripts/sync-core.js:28)
vendors six of the nine dual-mode modules. `lectio-file.js`, `moodle-sso.js` and
`oauth-redirect.js` are not vendored — correct for the latter two (their
platform work happens in main), but `lectio-file.js` is absent because the
renderer never adopted it. See §2.4.

- **Risk:** low to flag, medium to act on. Converging the desktop onto core

### 2.7 `start.command` — redundant with `npm start`

- **Path:** [start.command](packages/desktop/start.command)
- **Why flagged:** an 11-line wrapper that `cd`s, conditionally runs
  `npm install`, then runs `npm start`. It `cd`s to its own directory
  (`packages/desktop`) and checks for `./node_modules` there — but in this
  workspace, deps are hoisted to the repo root and `packages/desktop` has no

- **Risk:** low to remove; it is referenced only by
  [README.md:137](README.md:137) and [README.md:302](README.md:302). Removing
  it means editing those two lines. The alternative — fixing it to `cd` to the
  repo root — is roughly the same effort and keeps a double-click affordance.
  Either way it should not stay as-is.

## 3. Test coverage gaps

Every `packages/core/src` module has a corresponding test file, and **no test
references a function or file that no longer exists** — the `.test.js` names
cited in [USER_STORIES.md](docs/planning/USER_STORIES.md) (`ipc`,
`pomodoro-core`, `progress`, `semester-manager`, `semester`, `status`) all
resolve. Gaps below are within-module.

### 3.1 Three IPC handlers registered but never exercised

[ipc.test.js:38-47](packages/core/tests/integration/ipc.test.js:38) asserts
that `export-course`, `export-semester` and `import-file` are *registered*, then
tests only the four semester channels. The three export/import handlers
([ipc-handlers.js:19-51](packages/core/src/ipc-handlers.js:19)) have **no
behavioural test at all** — not their happy path, not their `filePath required`
guard, not `import-file`'s `File not found` branch or its `JSON.parse` throw on
a malformed file.

This is the most substantive gap: these handlers do unguarded filesystem writes
(§4.4) and are the only core code touching arbitrary paths.

### 3.2 `assertStorage` negative paths untested

[contract.js:14-24](packages/core/src/storage/contract.js:14) is called in two
tests ([fs-storage.test.js:21](packages/core/tests/unit/fs-storage.test.js:21),
[desktop-supabase-storage.test.js:21](packages/core/tests/contract/desktop-supabase-storage.test.js:21))
but only ever with a **valid** adapter. Neither rejection branch — `must be an
object`, `missing method: ${m}` — is ever reached, and `STORAGE_METHODS` is
never asserted. The validator's whole job is failing correctly, and that half is
untested.

### 3.3 `PROTECTED_TAG_IDS` has no direct test

Zero references in `packages/core/tests`. It is covered transitively through
`isProtectedTag` (3 test references), so the behaviour is exercised; the
constant's membership is not.

### 3.4 `setFreeStudyTime` is tested but unused

The inverse of the usual gap, and worth recording alongside §2.3: 5 test
references, 0 production callers. Coverage here does not indicate a shipped
code path.

### 3.5 Coverage accounting caveat

[vitest.config.mjs](packages/core/vitest.config.mjs) scopes coverage to
`src/**/*.js` with 70% line/function thresholds. Because every dual-mode module
defines its API twice from the coverage tool's perspective (the ESM import path
and the CJS path), new functions added to `planner-core.js` need a CJS-surface
test through
[require-core.cjs](packages/core/tests/helpers/require-core.cjs) — three test
files already do this (`breakdown`, `items`, `semester`, `sort`). Modules
consumed only via ESM import (`pomodoro-core`, the integrations) have no such
helper, so their CJS branch is unexercised.

### 3.6 Untested by design, for the record

`main.js`, `preload.js`, `app.js` and `style.css` carry no automated tests;
CLAUDE.md states this is deliberate (hidden-window Electron smoke tests run ad
hoc, outside CI). That is a stated policy, not drift — but it is why §4.5's
drag-and-drop defect could regress silently.

## 4. Security / IPC surface review

### 4.1 `contextIsolation` / `nodeIntegration` — intact everywhere

All five `BrowserWindow` constructions set `contextIsolation: true` and
`nodeIntegration: false`:

| Window | Location |
| --- | --- |
| Main window | [main.js:45-48](packages/desktop/main.js:45) |
| Legal doc window | [main.js:118](packages/desktop/main.js:118) |
| Pomodoro popup | [main.js:366-370](packages/desktop/main.js:366) |
| Moodle SSO capture | [main.js:679-681](packages/desktop/main.js:679) |
| OAuth capture | [main.js:723-725](packages/desktop/main.js:723) |

No `webSecurity: false`, no `sandbox: false`, no `enableRemoteModule`, no
`allowRunningInsecureContent` anywhere. `ipcRenderer` is never exposed.

### 4.2 `open-external` allowlist — intact, and not weakened elsewhere

[main.js:571-580](packages/desktop/main.js:571) still parses the URL and
requires `protocol === 'https:'` **and** `hostname === 'github.com'`, returning
a resolved no-op otherwise and swallowing malformed URLs. `shell.openExternal`
appears exactly once in the codebase — inside that guard — so there is no
second, weaker path to the OS URL handler.

The check itself is sound: `new URL()` normalizes before the hostname compare,
so `https://github.com.evil.tld` and `https://evil.tld/?x=github.com` both fail.
(As noted in §2.1, nothing calls it today.)

### 4.3 Semester `id` validation — consistent across all four adapters

The `[A-Za-z0-9_-]+` guard is applied before any id reaches a path or a row key,
in every adapter, with identical error text:

| Adapter | Guard | Applied in |
| --- | --- | --- |
| [semester-store.js:10](packages/core/src/semester-store.js:10) | `typeof id === 'string' && /^[a-zA-Z0-9_-]+$/` | `get` :27, `save` :35, `delete` :43 |
| [supabase-storage.js:64](packages/desktop/supabase-storage.js:64) | same regex | :89, :102, :140 |
| [supabase-storage.ts:10](packages/mobile/src/storage/supabase-storage.ts:10) | same regex | :33, :46, :85 |
| [device-storage.ts:12](packages/mobile/src/storage/device-storage.ts:12) | same regex | :28, :35, :41 |

Core's version is the strongest — it is the only one that also checks
`typeof id === 'string'`, so a non-string reaching the three adapter copies
would hit `regex.test(undefined)` (coerces to `"undefined"`, which *passes* the
character class). Not exploitable in the desktop's case because the same value
crosses IPC and is re-checked by `semester-store`, but the three copies are
strictly weaker than the original and the divergence is unintentional.

Every id-accepting IPC handler routes through `semester-store`:
`get-semester` / `save-semester` / `delete-semester` via
[ipc-handlers.js:14-17](packages/core/src/ipc-handlers.js:14), and
`load-example-semester` via `getSemester`/`saveSemester`
([main.js:494-499](packages/desktop/main.js:494)) with an id read from the
bundled `example.json`. `list-semesters` takes no id.

The traversal guard is covered by test —
[storage-contract.js:60](packages/core/tests/contract/storage-contract.js:60)
asserts `get('../secret')` rejects — and that suite runs against both
`fs-storage` and the desktop Supabase adapter.

### 4.4 Handlers accepting a path or URL from the renderer without validation

Four, in two groups.

**(a) Arbitrary filesystem paths — `export-course`, `export-semester`,
`import-file`**
([ipc-handlers.js:19](packages/core/src/ipc-handlers.js:19),
[:31](packages/core/src/ipc-handlers.js:31),
[:45](packages/core/src/ipc-handlers.js:45))

Each checks only `if (!filePath || typeof filePath !== 'string')` and then calls
`fs.writeFileSync` / `fs.readFileSync` on it. There is no directory
confinement, no extension check, no requirement that the path came from a
dialog. The renderer is *expected* to obtain the path from `show-save-dialog` /
`show-open-dialog` first
([app.js:3787](packages/desktop/app.js:3787),
[app.js:3947](packages/desktop/app.js:3947)), but the main process does not
verify that — it will write JSON to any path the process can reach, and read
any file back into the renderer.

Severity today is low: with `contextIsolation` on and only local `<script>`s in
the renderer, there is no untrusted code in the calling context. It becomes
real if renderer-side script injection ever lands (see 4.6), and it is the
single largest unguarded surface. A dialog-issued path allowlist (main keeps the
paths it handed out and only accepts those back) or an extension/confinement
check would close it. Note this is also the code with no behavioural test (§3.1).

**(b) Arbitrary URLs loaded into a BrowserWindow — `moodle-capture-token`,
`oauth-capture-redirect`**
([main.js:757](packages/desktop/main.js:757),
[main.js:758](packages/desktop/main.js:758))

`captureMoodleToken(baseUrl)` passes the renderer's `baseUrl` through
`buildLaunchUrl` — which does run it through `new URL()`
([moodle-sso.js:43](packages/core/src/integrations/moodle-sso.js:43)), so
malformed input throws — and then `authWindow.loadURL(launchUrl)`
([main.js:703](packages/desktop/main.js:703)). There is **no scheme check**:
`buildLaunchUrl('file:///etc')` produces a valid `file://` URL. Same for
`captureOAuthRedirect(oauthUrl)`, which calls `loadURL` on the renderer's string
with no parsing at all ([main.js:745](packages/desktop/main.js:745)).

Both windows are correctly isolated (4.1) and both intercept their redirect
before navigation
([main.js:698-699](packages/desktop/main.js:698),
[main.js:742-743](packages/desktop/main.js:742)), so the exposure is "renderer
can make the app display an arbitrary page in a chrome-less window", not code
execution. Requiring `https:` in both would cost two lines.

### 4.5 Related defect: drag-and-drop import is reading a removed API

[app.js:4011](packages/desktop/app.js:4011) reads `file.path` from a dropped
`File`, with the comment "Electron exposes the real fs path on File objects in
the renderer." That augmentation was removed; the shipped typings for the
pinned Electron 43.2.0 say so directly —
`webUtils.getPathForFile` "superseded the previous augmentation to the `File`
object with the `path` property"
(`node_modules/electron/electron.d.ts:19618-19628`). `file.path` is therefore
`undefined`, and the guard on the next line turns every drop into "Only
.lectio.json files can be dropped here."

Flagged here rather than as a bug fix because this audit changes nothing. The
fix is a `getPathForFile` call in preload exposed as a bridge method; the reason
it went unnoticed is §3.6.

### 4.6 Hardening gaps (no current exposure, cheap to close)

- **No `setWindowOpenHandler`** on any window. The only `will-navigate` /
  `will-redirect` handlers are the two auth-capture interceptors; neither
  window denies `window.open`, and neither the main window nor the two windows
  that load *remote* content restrict navigation. Electron's own guidance is
  to deny by default.
- **No Content-Security-Policy** in
  [index.html](packages/desktop/index.html) or
  [pomodoro-popup.html](packages/desktop/pomodoro-popup.html). All 14 scripts
  are local siblings and there is no remote script load, so nothing is
  currently violated — a CSP would be defence-in-depth against any future
  injected content, and would bound the impact of 4.4(a).
- **`openLegalDocWindow` interpolates HTML into a `data:` URL**
  ([main.js:106-112](packages/desktop/main.js:106)). Safe as written: `docKey`
  is allowlisted against `LEGAL_DOCS`
  ([main.js:89-92](packages/desktop/main.js:89), returning early on a miss), and
  the fragment comes from repo-bundled files, never user input. Noted only
  because the pattern (string-concatenated HTML into a navigable URL) is one to
  keep an eye on if those documents ever become editable.

Moodle tokens are handled well and deserve saying so: encrypted at rest through
`safeStorage` ([main.js:622-630](packages/desktop/main.js:622)), never written
in plaintext, and `listMoodleAccounts` deliberately strips `wstoken` before
returning to the renderer
([main.js:636](packages/desktop/main.js:636)).

## 5. Documentation drift

### 5.1 The monorepo question, answered directly

The brief asks whether
[ROADMAP_TO_LAUNCH.md](docs/planning/ROADMAP_TO_LAUNCH.md)'s "Current baseline"
overstates a monorepo that doesn't exist. **It does not — the roadmap is
correct and the brief's premise is inverted.** The monorepo is real:

- `packages/` exists with `core/`, `desktop/`, `mobile/`;
- [package.json:6-8](package.json:6) declares `"workspaces": ["packages/*"]`;
- all three packages publish their own `package.json` with the scoped names
  `@lectio/core` (1.8.8), `@lectio/desktop` (1.1.5), `@lectio/mobile` (1.1.5);
- `@lectio/desktop` depends on `"@lectio/core": "1.8.8"` and `@lectio/mobile`
  on `"@lectio/core": "*"`;
- the root scripts delegate with `--workspace`;
- CI runs `npm ci` at the root and uploads `packages/core/coverage/`.

**CLAUDE.md and README.md also describe the monorepo, not a single-package
layout** — CLAUDE.md's "Architecture" section and README's structure tree at
[README.md:283-345](README.md:283) both show `packages/`. There is no
three-way disagreement about the shape of the repo. There is no `lib/`
directory, no root `main.js`, no root `tests/`, and no `docs/PENDING_FEATURES.md`
(it lives at `docs/planning/PENDING_FEATURES.md`).

The real drift is narrower and listed below.

### 5.2 The stale claim repeated in three documents: "desktop is not wired to Supabase"

This is the most consequential piece of drift, and it appears verbatim-ish in
all three planning documents:

- **CLAUDE.md:** "Sync is currently **mobile-only**: desktop still uses
  `fs-storage` and is not wired to Supabase, so cross-device sync works
  mobile↔mobile."
- **PENDING_FEATURES.md:9-10:** "Cross-device **sync is mobile-only so far** —
  desktop is not yet wired to Supabase, so it does not sync with mobile or
  across machines."
- **ROADMAP_TO_LAUNCH.md:24-25:** "`@lectio/desktop` (Electron, fs-storage,
  feature-complete)".

The desktop **is** wired to Supabase:

- [supabase-client.js](packages/desktop/supabase-client.js) builds
  `window.lectioSupabase`;
- [auth.js](packages/desktop/auth.js) is a full renderer auth layer
  (`getSession`/`onAuthChange`/`signIn`/`signUp`/`signOut`);

  `if (signedIn && window.lectioSupabaseStorage) return window.lectioSupabaseStorage;`
- [local-import.js](packages/desktop/local-import.js) exists specifically to
  migrate local fs semesters into the cloud account;
- [sync-supabase.js](packages/desktop/scripts/sync-supabase.js) runs on
  `prestart`/`predev`/`prebuild` and **fails the CI build** when the Supabase
  keys are missing;
- CI passes `EXPO_PUBLIC_SUPABASE_*` secrets to the desktop packaging job
  ([ci.yml](.github/workflows/ci.yml));
- the adapter is under test against the shared contract suite

Anyone reading the docs would conclude cross-device sync is unbuilt on desktop.
It shipped.

## 6. Core package question: split `lib/` into a separate package, or not?

### 6.1 The question as posed no longer applies

The brief asks whether to extract `lib/` into a standalone `@lectio/core`
workspace "given the app is currently desktop-only". Both premises are false as
of this commit:

1. **The split already happened.** `@lectio/core` exists at
   [packages/core/](packages/core/) with its own `package.json`, its own
   version lineage (1.8.8 against the apps' 1.1.5), a 14-entry `exports` map,
   and its own Vitest config and coverage thresholds. There is no `lib/`.
2. **The app is not desktop-only.** `@lectio/mobile` is a real Expo app —
   19 route files, 40+ source modules, its own test suite, an EAS build
   configuration, and a shipped `app.json` with a live EAS project id.

So the decision isn't ahead of us. What's worth answering instead is whether
the split **earned its keep**, since that determines whether to keep investing
in it or unwind it.

### 6.2 What it actually bought

Concretely, and measurably:

- **A second consumer that reuses rather than reimplements.** Mobile imports
  core across at least 30 call sites. `getCourses` appears in 7 mobile files,
  `SORT_ORDERS` in 3, `editItem` in 3, `transfer.ts` pulls 8 exports from
  `lectio-file` in one import. None of the planner math is duplicated in
  TypeScript.
- **Exports that exist only because mobile needed them.** `editItem`,
  `deleteItem`, `reorderCourses`, `editCourseName`, `editCourseColor`,
  `getCourses` and `SORT_ORDERS` have **zero desktop callers** and multiple
  mobile ones (§2 cross-reference). These are core functions that exist
  *because* there are two consumers — the clearest possible evidence the
  boundary is load-bearing.
- **One storage contract with four implementations.**
  [contract.js](packages/core/src/storage/contract.js) plus the reusable
  [storage-contract.js](packages/core/tests/contract/storage-contract.js) suite
  let `fs-storage`, desktop `supabase-storage`, mobile `supabase-storage` and
  `device-storage` be genuinely interchangeable — identical id guards, identical
  error strings, identical migrate-on-load (§4.3). That uniformity is what made
  desktop cloud sync (§5.2) an adapter swap at
  [app.js:107](packages/desktop/app.js:107) rather than a rewrite.
- **Conflict resolution written once.**
  [conflict.js](packages/core/src/storage/conflict.js) is shared by both
  Supabase adapters; its comment names both consumers explicitly.
- **A stable seam for the third consumer.**
  [moodle-sso.js:6-9](packages/core/src/integrations/moodle-sso.js:6) already
  anticipates it: "The platform layer (packages/desktop now, later
  packages/mobile) is responsible for actually opening a browser/window" — and
  mobile's `src/moodle/` then delivered exactly that.

### 6.3 What it costs, honestly

The costs the brief anticipates are real and visible in this repo:

- **The vendoring apparatus.** Because the renderer is sandboxed and can't
  `require()`, `sync-core.js` must copy six core files next to `index.html` on
  every `prestart`/`predev`/`prebuild`, keep them git-ignored, and cross-check
  them against the electron-builder `files` allowlist — with a hand-written
  guard ([sync-core.js:36-50](packages/desktop/scripts/sync-core.js:36)) that
  exists because "the two lists have drifted apart before".
- **The dual-mode wrapper tax.** Nine modules carry the UMD-ish
  `(function (global, factory) {…})` preamble purely to satisfy three loaders,
  and it distorts coverage accounting (§3.5) enough to need a dedicated
  [require-core.cjs](packages/core/tests/helpers/require-core.cjs) helper.
- **Hand-maintained types.**
  [lectio-core.d.ts](packages/mobile/types/lectio-core.d.ts) is a hand-written
  ambient declaration file (250+ lines) mirroring a JS package, kept in sync
  manually and wired through `tsconfig` paths.
- **Packaging complexity.** `bundle-deps.js` + `clean-deps.js` exist solely
  because npm hoists workspace deps and electron-builder can't cope
  (CLAUDE.md's "Packaged build deps" gotcha), and `electron` has to be pinned
  to an exact version for the same reason.

### 6.4 Recommendation

**Keep the split, and stop treating it as provisional.** Do not unwind it, and
do not add a fourth package yet.

The reasoning is that the "wait for a second consumer" test — the right test,
and the one the brief correctly proposes — has already been met and passed. A
second consumer exists, it is substantial, and it demonstrably drove API into
core that the first consumer never needed (§6.2). The abstraction is not
speculative: it is being paid for by use. Unwinding it now would mean
reimplementing planner math, the storage contract, conflict detection and the
Moodle mapper in TypeScript for mobile — reintroducing precisely the drift that
§2.5's four copies of `slugify` illustrate at a much smaller scale.

The costs in §6.3 are real but they are *packaging* costs, not *boundary* costs.
Every one of them traces to a single constraint — the sandboxed renderer can't
`require()` and there is no bundler in the desktop build — not to the existence
of `@lectio/core`. They would mostly disappear behind a bundler step for the
renderer and would mostly persist if core were folded back in.

Two concrete follow-ups make the boundary pay off further, both already
identified above and both cheap:

1. **Finish the migration into core rather than starting a new one.**
   [lectio-file.js](packages/core/src/integrations/lectio-file.js) is core's
   canonical `.lectio.json` logic and only mobile uses it; the desktop still
   carries its own copy in `app.js` and `ipc-handlers.js`, and `slugify` exists
   four times (§2.4, §2.5). Converging these is the highest-value core work
   available and needs no new package — just a seventh entry in `sync-core.js`.
2. **Make the docs describe the system that exists** (§5.2 especially). The
   docs currently tell a reader that desktop sync is unbuilt, which is the
   single most misleading thing in the repo and actively undercuts the case for
   the shared core, since cloud sync on two platforms is the split's biggest
   payoff to date.

Where a genuine "not yet" judgement still applies is a **fourth** package: there
is no case for extracting a `@lectio/ui`, a `@lectio/supabase` or similar today,
even though `supabase-storage.js` and `supabase-storage.ts` are near-mirrors of
each other. Two implementations in two languages for two runtimes, already held
in agreement by a shared contract test, is the cheaper arrangement. Revisit only
if a third platform appears.
